# Sunny HRM — розгортання на сервері + інформаційна безпека
Єдина інструкція. Виконує IT-адмін на сервері Hetzner. Клод доступу до сервера не має.

---

## 0. Що всередині цього набору
```
sunny-hrm/
├─ docker-compose.yml      # весь стек: PostgreSQL + бекенд + Caddy(HTTPS)
├─ .env.example            # конфігурація (скопіювати у .env)
├─ db/init/00_app_role.sh  # створює НЕсуперюзерну роль застосунку (для RLS)
├─ caddy/Caddyfile         # HTTPS-проксі
├─ frontend/index.html     # погоджений інтерфейс (роздається сервером)
└─ backend/                # Node.js (Fastify) + міграції бази
```
Один контейнер-стек. Дані — у Docker-volume `pgdata` (переживають оновлення коду).

---

## 1. Передумови
- Сервер Hetzner (Ubuntu 22.04+), 2 CPU / 4 ГБ RAM / 40 ГБ — цього достатньо на ~140 людей.
- Встановлені **Docker** і **Docker Compose** (`docker --version`).
- Домен, напр. `hr.sunny.ua`, що вказує на сервер (A-запис).
- Доступ до **Google Workspace admin** і **Google Cloud Console** (для SSO і пошти).
- Корпоративний **OpenVPN** (у вас уже є).

## 2. Запуск (5 кроків)
```bash
# 1) покласти цей набір на сервер (scp/git) і зайти в теку
cd sunny-hrm
# 2) конфіг
cp .env.example .env && nano .env       # заповнити паролі, домен, Google, SMTP
# 3) переконатися, що погоджений HTML лежить у frontend/index.html
# 4) підняти стек (збере образи, застосує міграції, підніме БД+бекенд+Caddy)
docker compose up -d --build
# 5) перевірити
docker compose ps
docker compose logs -f backend        # має бути "[migrate] up to date" і "listening"
```
Готово — портал відкривається на `https://<ваш домен>`.

## 3. Перший вхід (bootstrap-адмін)
У базі створюється один адмін-акаунт (пошта з `001_init.sql`, за замовч. `admin@sunny.ua` —
**замініть на реальну перед першим запуском**). Пароля немає: адмін входить через **Google**
(перший вхід активує акаунт) або через «Забули пароль?» → лист → задати пароль.
Далі HR через «Імпорт співробітників» завантажує решту людей — усім летять запрошення.

---

## 4. Вхід через Google (опційно — «Продовжити з Google»)
Пошта в системі НЕ обмежена доменом: самостійна реєстрація і вхід поштою/паролем
працюють без жодного налаштування Google. Цей розділ — лише якщо хочете додатково
дозволити вхід одним кліком через Google.
1. Google Cloud Console → створіть проєкт → **APIs & Services → Credentials**.
   Це безкоштовно — білінг-акаунт не потрібен для звичайного OAuth-логіну.
2. **Create Credentials → OAuth client ID → Web application**.
3. **Authorized JavaScript origins:** `https://hr.sunny.ua` (для локального тесту — `http://localhost:8080` чи який у вас порт).
4. **Authorized redirect URIs:** `https://hr.sunny.ua` (і `/activate`, якщо знадобиться).
5. Скопіюйте **Client ID** у `.env` → `GOOGLE_CLIENT_ID`.
6. Consent screen можна лишити в режимі **Testing** (без верифікації Google) — додайте свій
   Google-акаунт у список тестових користувачів (до 100 акаунтів, безкоштовно).
> Вхід через Google дозволений лише для пошт, які вже є в базі співробітників —
> це перевіряє бекенд (`auth.routes.js`), а не сам Google.

## 5. Пошта (запрошення, відновлення пароля) — SMTP
1. Найпростіше для тесту/невеликої команди — звичайний Gmail: увімкніть 2FA на акаунті,
   створіть **App Password** (Google Account → Security → App passwords, 16 символів).
2. У `.env`: `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_USER=<ваша адреса>`,
   `SMTP_PASS=<app password>`, `MAIL_FROM="Sunny HR <ваша адреса>"` (Gmail вимагає, щоб
   адреса у `MAIL_FROM` збігалась із автентифікованим акаунтом).
3. Для Google Workspace-релею — `Google Admin → Apps → Gmail → Routing → SMTP relay service`.
> Якщо SMTP не налаштований — бекенд НЕ падає: посилання-запрошення пишеться в логи
> (`docker compose logs backend`), зручно для тесту.

## 5а. ШІ-помічник і оцінка резюме (опційно, безкоштовно)
Обидві функції — окремий, незалежний шар, вимикаються самі, якщо ключа немає:
1. **Рекомендовано (безкоштовно назавжди, без картки):** зайдіть на
   `aistudio.google.com`, увійдіть Google-акаунтом → **Get API key** →
   скопіюйте в `.env` → `GEMINI_API_KEY`. Ліміт безкоштовного рівня —
   орієнтовно 1000-1500 запитів/добу для моделі Flash, цього достатньо
   для навчального/тестового навантаження.
2. **Альтернатива:** якщо є платний доступ до Claude — `ANTHROPIC_API_KEY`
   у `.env` (використовується, лише якщо `GEMINI_API_KEY` порожній).
3. `GEMINI_MODEL` / `ANTHROPIC_MODEL` — за замовчуванням дешеві швидкі моделі;
   можна змінити на іншу за потреби.
4. Без жодного ключа: чат і кнопка «Оцінити резюме» показують повідомлення
   «ШІ не налаштований» замість помилки — решта системи не зачіпається.

## 6. Інформаційна безпека (6 шарів)

**Шар 1 — VPN (OpenVPN).** Портал має відповідати лише зсередини VPN. Два способи:
- **Файрвол сервера:** відкрити 80/443 лише для підмережі VPN, напр.:
  ```bash
  ufw default deny incoming
  ufw allow 22/tcp                      # SSH (краще теж лише з VPN)
  ufw allow from 10.8.0.0/24 to any port 443 proto tcp   # ← ваша VPN-підмережа
  ufw allow from 10.8.0.0/24 to any port 80  proto tcp
  ufw enable
  ```
- **Або в Caddy** обмежити за IP (`@vpn remote_ip 10.8.0.0/24` + `respond @novpn 403`).
> Уточніть у себе реальну VPN-підмережу й підставте замість `10.8.0.0/24`.

**Шар 2 — HTTPS (Caddy).** Сертифікат автоматично. **За VPN** стандартна перевірка Let's Encrypt
не працює (сервер не видно ззовні) → використайте **DNS-челендж**: у `caddy/Caddyfile`
розкоментуйте блок `tls { dns <провайдер> {env.TOKEN} }`, додайте токен DNS-провайдера в `.env`
і відповідний образ Caddy з плагіном DNS. (Якщо портал усе ж доступний ззовні — нічого не треба.)

**Шар 3 — паролі.** Зберігаються лише як **bcrypt-хеш** (кост 12), ніколи відкритим текстом.

**Шар 4 — модель автентифікації.** Домен пошти нічим не обмежений — самореєстрація
дозволяє будь-яку адресу (у т.ч. звичайну @gmail.com). Опційний Google-вхід додатково
звіряє пошту з базою вже існуючих співробітників, тож новий акаунт через Google
створити не можна — лише через звичайну реєстрацію поштою/паролем.

**Шар 5 — приватність на рівні бази (RLS).** Бекенд ходить під НЕсуперюзерною роллю `hrm_app`,
до якої застосовуються політики. Приклад-флагман — на таблиці `requests`.
> DEV-REVIEW: розширити RLS на `employees` (з урахуванням прихованого року народження через view),
> `approvals`, `survey_responses`, `security_log`, `audit_log` (окремі міграції 002+).

**Шар 6 — моніторинг/алерти + журнали.** `security_log` (спроби входу; IP/пристрій зберігаються, але
в інтерфейс не віддаються), `audit_log` (хто що змінював). Автоблокування після 5 невдалих спроб на
15 хв + ручне розблокування HR.

**Бекапи (окремо від сервера, зашифровані):**
```bash
# щоденний дамп + шифрування + вивезення в ІНШЕ місце (S3/інший хост)
docker compose exec -T db pg_dump -U hrm_admin sunny_hrm | gzip | \
  gpg --symmetric --cipher-algo AES256 -o /backups/hrm-$(date +%F).sql.gz.gpg
```
Поставте в cron і **зберігайте копії не на цьому ж сервері**. Перевіряйте відновлення раз на місяць.

## 7. Оновлення коду без втрати даних
```bash
git pull            # або залийте нову версію файлів
docker compose up -d --build
```
Volume `pgdata` не чіпається → усі співробітники, заяви, історія лишаються. Нові зміни структури —
лише новими файлами `backend/migrations/002_*.sql` (застосуються самі на старті).

## 8. DEV-REVIEW — обовʼязково перед бойовим запуском
1. **Підключити інтерфейс до API.** Погоджений `frontend/index.html` — це прототип, який зараз тримає
   дані у памʼяті браузера. Щоб він працював із бекендом, його виклики треба перенаправити на ці
   endpoint-и (`/api/...`, авторизація через cookie-сесію / Google). Це фінальний крок інтеграції —
   найкраще робити його теж під наглядом розробника (Клод може видати цю версію фронтенду окремо).
2. Реальна пошта bootstrap-адміна у `001_init.sql`.
3. RLS: переконатися, що бекенд ходить під `hrm_app` (не суперюзер), і `SET LOCAL app.*` є в кожній
   транзакції; розширити політики на решту таблиць.
4. Файли (фото, CV, KB): для проду винести у обʼєктне сховище (зараз — у БД).
5. Перевірити правило заборони накладання дат і ланцюжок погодження під ваші реальні кейси.
6. Секрети (`SESSION_SECRET`, паролі БД) — довгі й випадкові; `.env` не потрапляє в git.
